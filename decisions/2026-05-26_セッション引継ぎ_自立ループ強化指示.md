# 2026-05-26 セッション引継ぎ + 自立ループ強化指示 (YD)

## 決定

Project Agent Application の開発において、**builder ⇄ qa/design-evaluator** と **designer ⇄ design-evaluator** の自立ループ構造を本格運用する。YD が見る前に基本バグを全部潰した状態にする。

## 背景

### 今日 (2026-05-26) のセッション概要

深夜から朝にかけてのフルスプリント:
- 大方針再定義 (議事録ベース)
- 仕様書 Pass (planner ⇄ spec-reviewer 自立ループ 4 ラウンドで完成)
- designer Sprint 01 + 07 (第 1-2 弾) + 08-10 完了
- builder Sprint 01 初版完了 (Expo SDK 56)

### バグの流出経路 (YD への指摘)

builder Sprint 01 初版完了後、メイン Claude が qa/design-evaluator を起動せず YD の目視確認に依存した結果、以下のバグが YD に表面化:

| バグ | 発見経路 | 本来 evaluator が検出すべき |
|---|---|---|
| Web 対応漏れ (SecureStore) | YD の Web preview で「ExpoSecureStore.default.setValueWithKeyAsync is not a function」エラー | qa-evaluator が `expo export --platform web` で実行確認すべき |
| dev ボタン Android 限定表示 | YD「選択肢が出てこない」報告 | design-evaluator が「全プラットフォームで動作確認」検証すべき |

## 採用された方針

### 1. builder 完了 → qa-evaluator + design-evaluator 並列起動 (即座)

メイン Claude (orchestrator) は、builder 完了通知を受領した瞬間に:
1. **qa-evaluator** (機能要件 / tsc / ESLint / Web export / Detox) を BG 起動
2. **design-evaluator** (NG リスト 31 / ベンチマークパリティ / 5 ペルソナ体験 / 全プラットフォーム動作) を BG 並列起動
3. 両方の完了を待つ
4. Pass + Pass → 次 sprint 進行 (YD に「Sprint X 完了」のみ報告)
5. どちらか Fail → builder に SendMessage で修正指示 → 再 evaluator → Pass まで自走
6. **同 sprint で 3 回連続 Fail → YD エスカレーション**

### 2. designer 完了 → design-evaluator 起動 (即座)

メイン Claude は designer 完了通知を受領した瞬間に:
1. **design-evaluator** を BG 起動
2. 完了を待つ
3. Pass → builder 起動可能 (Sprint 02 以降の builder 着手は design Pass 後)
4. Fail → designer に SendMessage で修正指示 → 再 evaluator → Pass まで
5. 3 回連続 Fail → YD エスカレーション

### 3. orchestrator (メイン Claude) の新しい役割

旧:
- builder 完了 → YD に報告 → YD が動作確認 → バグ発見 → 修正指示

新:
- builder 完了 → **即 evaluator 起動** (YD に見せない)
- 自立ループで Pass まで自走
- YD への報告は「全部完了して動く状態」のみ
- 中間進捗報告は禁止 (YD の認知負荷削減)

### 4. YD への対応原則

- 「ガンガン進める」テンションは維持
- だが「中途半端な完成」を見せない、Pass 確定したものだけ提示
- 設計判断 / 商標確認 / マネタイズ等の YD 固有判断のみ AskUserQuestion で確認

### 5. builder/evaluator のモデル独立 (2026-07-09 追記)

evaluator (qa-evaluator / design-evaluator) は builder/designer と **別モデル** で走らせる。同一モデルは同一バイアスを共有するため、独立した第三者検証にならない (P/G/E 分離の趣旨を保つ)。例: builder = gpt-5.5 / codex 系なら evaluator = claude 系、builder = claude 系なら evaluator を別系統に振る。

出典: 2026-07-09 Fable5記事の Verification Loop パターン (verifier ≠ executor)。詳細は [[vault_improvement_proposals]] 2026-07-09 バッチ ③。

## 採用された選択肢と却下案

| 案 | 採用 | 理由 |
|---|---|---|
| **A. メイン Claude が orchestrator (現状運用 + 即 evaluator 起動を厳守)** | ✅ | シンプル、リスク低、すぐ運用可。サブエージェントから別エージェント起動の複雑性回避 |
| B. builder/designer 自身が evaluator を起動するハーネス変更 (Agent ツール権限付与) | ❌ | サブエージェントから別エージェント起動はコスト高、通信複雑、メイン Claude の orchestrator 設計と矛盾 |
| C. evaluator を builder/designer の prompt 内に組み込み (完了報告と評価を 1 エージェントで実施) | ❌ | 第三者視点が失われる、ハーネス設計の本来の意図 (P/G/E 分離) を破壊 |

## ✅ うまく行ったこと

- YD の指摘が的確 (バグ流出経路 + ハーネス設計の運用ギャップを正確に指摘)

## ❌ 詰まったこと

- メイン Claude が「YD に目視確認してもらえばいい」と評価ステップを省略 → バグ流出 (Web 対応漏れ + Platform 限定 dev ボタン)
- planner ⇄ spec-reviewer は自立ループが機能していたが、builder/designer 側は手動運用に依存していた (ハーネス設計の片肺運用)
- セッション context 増大で長時間継続困難、引き継ぎ仕組みが未整備 → 急遽 HANDOVER.md 整備

## 📋 次回同様の判断をするときのチェックリスト

- **builder/designer サブエージェント起動時、完了通知後の "即 evaluator 起動" を必ず約束**
- メイン Claude のメッセージで「YD に確認してみてください」を多用しない (orchestrator は判定を YD に丸投げしない)
- 「YD の認知負荷削減」を意識: 中間状態は見せない、最終 Pass 確定のみ報告
- ハーネス設計 (Planner-Generator-Evaluator) は **全フェーズで** 機能させる、片肺運用を放置しない
- セッション context が 50% を超えたら HANDOVER.md 整備 + decisions/ 引継ぎを開始
- 走り中の Agent ID + output file path を必ず HANDOVER.md に記載

# PAA セキュリティ総合再監査 (2026-08-08)

YD 指示「一旦バックグラウンドとセキュリティ周りを総合チェックして、抜け漏れがあったら修正、追加してほしい」。

## 状況

`overhaul/2026-07` ブランチで全面改修 (3 Wave) が完了した状態。過去に 2 回のセキュリティ監査
(2026-06-04 の critical2+high8、2026-07-13 の BACK-1〜7) を実施済みで、いずれも「修正済み」と記録されていた。

## 選んだ方針

**4 系統の独立監査を並列で回し、過去に「修正済み」とされた項目も自己申告を信じず全件再検証する**。

- audit-edge: Edge Functions 12 本 + config.toml
- audit-db: migration 001〜022 の累積適用状態 (テーブル台帳を作らせる)
- audit-client: 認証 / データ層 / Storage / 通知
- audit-config: 秘密情報スキャン / .gitignore / eas.json / 依存

理由: 過去監査は「その時点のコード」に対する判定で、**その後の Wave で状況が変わった項目を検出できない**。
実際これが的中し、最重要の発見 (022 の前提崩壊) につながった。

## 結果: 60+ 所見。P0/P1 は実コードで裏取り

| ID | 内容 |
|---|---|
| EDGE-01 | SSRF ブロックリストが IPv4-mapped IPv6 (`[::ffff:10.0.0.5]`) で回避可能。WHATWG URL が 16 進正規化するため 10 進期待の正規表現が効かない。修正後にバイパス 27 種 + 正常系 4 種を **node で実行検証** |
| EDGE-05 | `reminders-leader-nudge` が `assigneeIds` を実アサイニーと照合せず、自 PJ リーダーが任意ユーザーへ「**被害者本人のキャラ名義**」で Push 送信可能 = フィッシング媒体 |
| EDGE-07 | 招待消化が read-then-write レース。同一トークンの同時消化で二重参加 |
| CLIENT-01 | PKCE 運用なのに implicit (`#access_token`) 経路が残存。細工リンクを踏ませるだけで victim を攻撃者アカウントにログインさせられる (login CSRF) |
| CFG-01 | `eas.json` が参照する `google-play-service-account.json` がどの .gitignore にも無い。**GitHub リモートが実在**するため、Play 提出時に鍵を作った瞬間 `git add .` で公開される |
| DB-02 | `submissions.created_at` をクライアントが任意指定でき、トリガーがそれを `submitted_at` にコピー → on-time 率が常に 1.0 でポイント 1.2 倍 |
| DB-03 | 招待で入った一般メンバーが自分の招待行を UPDATE して `used_at` を消せる → 使い捨て 7 日リンクが**無期限・無制限の入口**に |

## ★ 最重要の発見: migration 022 の前提が崩れていた

022 のヘッダは「`useUpdateTaskStatus` は呼び出し元ゼロの死にコード (grep 済)」と明記していたが、
これは **2026-07-13 時点の事実**で、その後の Wave 2 でホーム長押し完了に配線された
(`app/(tabs)/index.tsx:970`、SC-2 コメント付き)。

022 を単独適用すると実モードのタスク完了が全ユーザーで RLS 42501 になり、しかも楽観 UI が先に
カードを消すため「消えたのに次回起動で復活」を全員が踏む。**DB 監査とクライアント監査が独立に同一結論**に到達。

→ 022 は適用保留。022 が塞ごうとしたポイント水増しは、023 の DB-02 修正 (トリガーを `now()` 化) のほうが根治に近い。

## ✅ うまく行ったこと

- **4 系統の独立並列監査**が効いた。同じ穴 (022 の前提崩壊) に DB 監査とクライアント監査が別経路で到達し、
  相互に裏付けが取れた。単一監査なら見落とすか、確信が持てなかった
- **監査に「過去の修正の再検証」を明示的に含めた**こと。「修正済み」ラベルを信じない設計が最大の発見を生んだ
- **修正の実行検証**。SSRF ガードを関数ごと抽出して node で 31 ベクタを実行 (Node 24 のネイティブ TS ストリップが便利)。
  「直したつもり」を排除できた
- 監査エージェントに「✅確認済み一覧」を必ず書かせたこと = カバレッジ証明になり、
  「調べていない」と「調べて問題なし」を区別できた
- ファイル所有権を分離した実装 4 便の並列化。競合ゼロ

## ❌ 詰まったこと

- **stale な `.git/index.lock`** (7/19 のクラッシュ由来) が 3 週間残っており `git rm --cached` が失敗。
  アクティブな git プロセスが無いことを `ps` で確認してから除去 (mistakes A-16/A-17 の規律を適用)
- 監査エージェントの完了通知 (idle) は届くが**レポート本文が自動では来ない**。SendMessage で明示的に
  依頼する必要があり、DB 監査は 3 回催促した。次回は「完了時に SendMessage でレポート全文を送れ」を
  プロンプトに最初から書く
- 監査中に YD からモデル方針の指示 (Fable 5 優先 / Opus 4.8 禁止) が入った。サブエージェントは
  `model` 未指定だと親セッションのモデルを継承するため、**明示指定が必要**と判明

## 📋 次回同じことをするときのチェックリスト

1. 監査プロンプトに「**過去に修正済みとされた項目も自己申告を信じず再検証せよ**」を必ず入れる
2. 監査プロンプトに「**完了時は SendMessage でレポート全文を team-lead に送れ**」を最初から書く
   (idle 通知だけでは本文が来ない)
3. 監査エージェントには「✅確認済み一覧」を必ず書かせる (カバレッジ証明 = 「未調査」との区別)
4. 「死にコード」「呼び出し元ゼロ」と書かれた**過去の判断は日付を確認**する。その後の実装で状況が変わる
5. セキュリティ修正は**実行検証**する (関数を抽出して既知の攻撃ベクタを流す)。コードレビューだけで終えない
6. 破壊操作 (`rm`, `git rm`) の前に実体確認 — 今回も `ps` で git プロセス不在を確認してからロック除去
7. サブエージェントに使わせたいモデルは `model:` で**明示指定**する (未指定 = 親セッション継承)
8. MOCK デモ保全は「分岐数の grep」+「シミュレータ実機表示」の 2 段で確認する

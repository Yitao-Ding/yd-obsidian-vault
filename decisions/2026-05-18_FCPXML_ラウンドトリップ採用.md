# FCPXML ラウンドトリップ方式の採用 (FCP内構造化変更)

## 背景

vidkit に autocut 機能 (無音カット FCPXML生成) を実装した直後、YDから
「FCPX内で自動的にClaudeが操作して、いじってみたいなことはできないのかな」
という質問が出た。

Final Cut Pro X (以下 FCP) に対して Claude が自動的に編集操作を行う方法を検討した。

## 選択肢

### 1. computer-use MCP で画面操作

GUI を画面ピクセル単位で操作する。Bキーでブレード、Cmd+Z、ボタンクリック等。

**長所**:
- 「FCPを開いて再生して」のような単純操作は現実的
- 視覚的に何が起きてるか分かる

**短所**:
- タイムライン上のピクセル精密な位置決めには脆い
- 「3分20秒にちょうどカット入れて」は厳しい
- FCP のレイアウト変更で全部壊れる
- 再現性が低い

### 2. AppleScript

macOS の伝統的なアプリ自動化方式。

**長所**: macOS ネイティブ、安定

**短所**:
- **Apple が意図的に FCP のスクリプティングを削った**
- できることは open / activate 程度
- 編集操作はほぼ不可能

### 3. FCPXML ラウンドトリップ

`File → Export XML` で書き出し → Claude が読んで構造変更 → `File → Import XML` で戻す。

**長所**:
- Auto-Editor / Recut / Trint など業界の自動化ツールは**全部これ**
- 構造化された一括変更が秒で終わる
- 「テロップを全部同じフォントに統一」「すべてのジャンプカット箇所にディゾルブ追加」「インタビューの相手の話だけ抽出」などが可能
- 再現性が高い、デバッグしやすい

**短所**:
- ユーザーが Export / Import を手動でやる必要 (Cmd+E, Cmd+I)
- リアルタイム操作はできない (バッチ処理寄り)

## 決定

**選択肢 3 (FCPXML ラウンドトリップ) を採用**

## 理由

1. **業界標準** — Auto-Editor / Recut / Trint など実績のあるツールが全て採用
2. **構造化変更との相性** — Claude の得意領域 (一括変換、フィルタ、抽出)
3. **既存実装との連続性** — vidkit autocut で既に FCPXML 生成は実装済み (一方向)
4. **再現性とデバッグ性** — XML は読める、テストできる、バージョン管理できる
5. **YDのユースケースに合致** — 「荒く並べた素材を一括処理」が中心

選択肢 1 は「ボタン押す」「ウィンドウ切替」程度のアプリ操作補助なら使えるが、
編集操作の主軸にはならない。補完的な選択肢として保留。

## 実装方針

### 最小単位

「FCPXMLリーダー + 1つ目の変換オペレーション」をセットで作る。

### 第一弾オペレーション: tighten

既存FCPプロジェクトの各クリップ内に残った無音をさらに詰める。

**理由**:
- いまの vidkit autocut の自然な延長
- 「FCPで荒く並べた → Claudeでもう一段詰める → 戻す」が成立する
- 一番実用価値が高い (検証済みの autocut 技術を流用できる)

### 候補オペレーション (将来)

| オペレーション | 内容 | 優先度 |
|-------------|------|------|
| tighten | クリップ内の残り無音を詰める | ★★★ (第一弾) |
| speaker-filter | 話者ベースで残す/削る (diarization要) | ★★ |
| marker-batch | トランスクリプトのキーワードでチャプターマーカー一括挿入 | ★★ |
| beat-snap | 既存カット点を音楽ビートにスナップ (蛹用途) | ★ |
| roles-bulk | 全クリップに同じFCP rolesを付与 (ステム分離用) | ★ |

## ユーザーワークフロー

```
1. FCP で素材を荒く並べる
2. File → Export XML (Cmd+E)
3. Claude Code に「tighten 適用して」と依頼
   → vidkit が XML を読んで処理 → 新しい XML を書き出し
4. FCP に戻り File → Import XML
5. 微調整して書き出し
```

ステップ 2 と 4 のクリックが必要なのが唯一の摩擦だが、これは FCP の制約。

## その後

第一弾の tighten オペレーションは未実装。次回のセッションで着手予定。

実装する際は以下を意識:
- vidkit autocut のコードを最大限再利用
- FCPXMLリーダーは汎用的に作る (他のオペレーションでも使える)
- 出力 XML は元 XML の構造を可能な限り保持 (FCP の挙動を予測しやすく)

## ✅ うまく行ったこと

- **業界事例の調査が決め手になった**: Auto-Editor / Recut / Trint といった既存自動化ツールが**全て FCPXML ラウンドトリップ方式**だと知ったのが、迷いを払拭した最大の要因。先行例があると安心して採用できる。
- **既存実装 (vidkit autocut) の自然な延長**: ゼロから新方式を作るのではなく、すでに動いている FCPXML 生成コードを「ラウンドトリップ対応」に拡張する形にできる。コスト効率がいい。
- **3つの選択肢を全部検討してから決めた**: computer-use / AppleScript / FCPXML ラウンドトリップを全て検証した上で選んだので、後で「もっと良い方法あったのでは」と迷わない。
- **第一弾オペレーション (tighten) の選定**: 「既存技術の流用度が最大」「YDの実ワークフローに直結」という基準で、迷いなく決められた。

## ❌ 詰まったこと

- **最初 "computer-use で操作" に期待してしまった**: 「ClaudeがFCPの中で実際にボタン操作してくれたらカッコいい」という幻想で、ピクセル精密制御の脆さに気づくのに時間がかかった。
- **AppleScript への淡い期待**: macOSアプリ自動化の伝統だから使えると思ったら、**FCP X は Apple が意図的にスクリプティングを削っている**という事実を知って驚いた。これは公式ドキュメントにも書いてないので調べないと分からない。
- **「ユーザーが Export/Import をクリックする手間」**: FCPXML ラウンドトリップの唯一の摩擦点。完全自動化したいなら computer-use で Export/Import だけ補助する併用も検討の余地あり (今回は保留)。

## 📋 次回同じ判断をするときのチェックリスト

### ネイティブアプリの自動化を検討するとき

- [ ] **公式スクリプティング API があるか確認** (AppleScript / Automation Scripts / Plugin SDK 等)
- [ ] **インポート/エクスポート可能なオープン形式があるか確認** (XML / JSON / CSV など)
  - あれば、ファイルベースのラウンドトリップが圧倒的に強い
- [ ] **業界の既存自動化ツールがどの方式を採用しているか調査**
  - 「成功してるツール = 一番現実的な道」のサイン
- [ ] **GUI操作 (computer-use) は最終手段**: ピクセル制御は脆い、レイアウト変更で壊れる
- [ ] **判断基準**: 再現性 > リアルタイム性 (ほとんどのケース)

### FCPXML ラウンドトリップで新オペレーションを作るとき

- [ ] **FCPXML リーダーを汎用的に**: パーサーは1つ、変換ロジックは分離する
- [ ] **出力 XML は入力 XML の構造を可能な限り保持**: FCP の挙動を予測しやすくする
- [ ] **既存 vidkit autocut のコードを最大限再利用**: フレーム計算、URL生成、シリアライザはすでにある
- [ ] **xmllint で出力検証 → 実機 FCP でインポートテスト**
- [ ] **テストプロジェクト用意**: 短い FCP プロジェクトを Export → 変換 → Import で往復確認

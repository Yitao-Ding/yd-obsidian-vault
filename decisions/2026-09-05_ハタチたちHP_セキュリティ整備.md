# ハタチたちHP セキュリティ整備の方針

YD「このサイトのバックグラウンド、セキュリティを整備して」を受けて、静的 Next.js 16 サイト (Vercel Hobby、$0) の守りを固めた。4観点 (ヘッダ/CSP、アプリコード、依存・リポジトリ、Vercel/DNS) の監査ワークフロー (24エージェント、13完了・11はセッション上限で落ちた) の結果に基づく。正本は repo の `docs/security.md`。

## 状況

本番のレスポンスヘッダは HSTS のみ。`*.vercel.app` の別名が同一内容を 200 で返す。`pnpm audit` 14件 (high 7) + pnpm audit に出ない critical 2件、全部 next 16.2.6 が根。GitHub は Dependabot 無効・ブランチ保護なし。Vercel 環境変数ゼロ。ただしサイトは静的でフォーム・認証・ユーザー入力が無く、監査の反証側は「16件とも現状の攻撃経路は無い、衛生管理」と評価。

## 選んだこと

- CSP は2本立て。enforce は `frame-ancestors 'none'; object-src 'none'; base-uri 'self'` の3つだけ、通信先の許可リストは Report-Only。理由: Next の静的ページは inline script が必須で `'unsafe-inline'` を外せない (外すと hydration が止まる、実測)。つまり CSP で inline XSS は止められず、得られるのは外部 script/frame の origin 制限のみ。それを enforce すると Instagram / YouTube の仕様変更で埋め込みが無言で消えるリスクを、Console を見ない運用者が引き受けることになる。割に合わない
- nonce 方式は採らない。全ページ動的レンダリングになり CDN キャッシュが効かなくなる
- next 16.3.4 / react 19.2.8 に更新。`pnpm audit --prod` 0件。16.2.11 では postcss/sharp と critical 2件が残るので 16.3.x が必要だった
- `hatachi-tachi-website.vercel.app` → `https://hatachitachi.com` 308 (完全一致ホストのみ。正規表現で `*.vercel.app` を掴むとプレビューまで飛ぶ)
- `/preview/news/…` は CMS 未接続 or draftKey 無しで 404
- `NEXT_PUBLIC_SITE_URL` を Vercel Production に明示 (自動判定は「最短のカスタムドメイン」なので、将来 studiometali.com を足すと揺れる)
- GitHub: Dependabot alerts + security updates ON、`dependabot.yml` 月1まとめ PR (メジャー除外)、ruleset で main の削除と force push 禁止 (PR 必須は入れない。ソロ運用で push=デプロイなので)
- pnpm: `minimumReleaseAge: 10080` (7日、next は除外)、`verifyDepsBeforeRun: install`
- やらない: HSTS includeSubDomains/preload、CAA、CI (Vercel が失敗ビルドを出さないので)、`/_next/image` の閉鎖 (未使用だが microCMS 用ローダーと絡む)、git 履歴のお名前ID消去 (force push が必要で ruleset と矛盾、ID 単体の価値が低い)

## YD の手作業 (コードで守れない)

1. お名前.com ドメイン情報認証メール、期限 2026-09-17 (踏まないと2ドメイン停止 → サイト全落ち)
2. お名前.com Navi の移管ロック ON + 2段階認証 (無料)。DNSSEC/ドメインプロテクションは有料なので入れない
3. GitHub / Vercel / Gmail の 2FA を認証アプリかパスキーに
4. Vercel Hobby の非商用条項。参加費徴収・協賛ロゴ・物販を載せるなら Support 確認か Pro
5. 外形監視 (UptimeRobot 等、任意)
6. 素材原本 `~/Downloads/ハタチたちhp/` の恒久保管

## ✅ うまく行ったこと

- 監査に先立って Performance API で「自サイトの document が直接読むリソース」だけを切り出したのが効いた。ネットワーク一覧には iframe 内部の通信 (cdninstagram / googlevideo / graph.instagram.com) が大量に混ざり、そのまま CSP に入れると許可リストが膨らむ
- 反証エージェントが本番に提案ヘッダを注入して enforce/Report-Only 両方で違反0を実測してくれたので、こちらの手元検証 (curl 7ヘッダ + Playwright で 1200/375、/、/news、/news/slug、404 の Console) と二重に取れた
- 監査の「high」を反証側が「low (衛生)」に格下げした判断は正しかった。脅威モデル (静的・入力なし) を先に共有しておくと、重大度のインフレが抑えられる

## ❌ 詰まったこと

- ワークフローの反証 11件 + クリティックがセッション上限 (21時リセット) で落ちた。24エージェント規模の並列は上限に届く。落ちた分は「未検証」として扱い、低リスクのものだけ採用した
- GitHub の secret scanning 「非プロバイダ汎用パターン」は API (PATCH security_and_analysis) で enabled にしても disabled のまま。UI からしか変えられない可能性。手作業リストへ
- `gh api -f 'a[b][c]=x'` のネスト指定は効かない。JSON を `--input -` で渡す
- 監査結果の出力ファイルはワークフロー全体のメタ JSON で、`{"confirmed"…}` を直接 raw_decode できない。個々の結果は `journal.jsonl` の `type: result` 行から取るのが確実

## 📋 次回同じことをするときのチェックリスト

1. まず curl -sI で本番ヘッダ、`pnpm audit --prod`、`gh api repos/…` の security_and_analysis、`vercel env ls` を取り、事実として監査プロンプトに埋め込む (エージェントの重複調査を減らす)
2. Performance API で document 直下のリソース origin を確定してから CSP を書く。iframe 内部の通信は対象外
3. 静的 Next サイトの CSP は `'unsafe-inline'` 前提。enforce するのは frame-ancestors / object-src / base-uri の3つ、通信先は Report-Only、と決めてよい
4. ヘッダ変更は `pnpm build && pnpm start` の本番ビルドで curl と Playwright (埋め込みを実際に発火させる) の両方で見る。dev サーバーでは CSP の `'unsafe-eval'` 分岐が違う
5. `minimumReleaseAge` は依存更新の**後**に入れる (直近7日の版が取れなくなる)。Vercel の frozen install には影響しない
6. 依存の更新は独立コミットにして、戻しやすくする
7. 反証エージェントは finding あたり high=2 / should-fix=1 に絞っても 20超になる。セッション上限を見て、監査4 + 反証10 程度に抑えるか2回に分ける

# 納品前に別エージェントの監査 → 反証 → 判定を通す

## 状況

構成v2 を YD に出したら全面差し戻しになった。噛みを使っている、丸窓が出ていない、字幕が単語の途中で改行している、顔の位置が逆、音がキモい。YD の言葉は「なんで噛んでる音声使うの？ちゃんと確認しろ」「細かい部分の出来悪すぎ」で、指示として「成果物にプロの監査役をつけろ」が出た。

v3 を作って引き継いだが、次のセッションで機械検査を掛けたら v2 と同種の不良がまだ残っていた。撮影場所の言い直しをそのまま採用していた (src 226〜232「海老名市立東柏…海老名じゃないかな。海老名市立東柏小学校」)、次の文の言いかけが 2 件尻に残っていた、カット境界で単語が切れているところが 15 か所、丸窓トラックが話者のいない間にスクリーンの文字や集合写真を顔として切り抜いていた (v3 の valid 区間の 17%)。自分で作ったものを自分で見ても、同じ見落とし方をするというのがはっきりした。

## 決めたこと

納品前に次の 3 段を必ず通す。

1. 洗い出し。別エージェントに 4 観点 (噛み・言い直し / 映像 QC / 字幕 / FCPXML 構造) を割り振って、それぞれ指摘を出させる。渡す文脈は `_cc_work/AUDIT_CONTEXT_v4.md` にまとめてある。クライアント要求と既知の制約を先に書いておかないと、仕様どおりの箇所を不良として大量に挙げてくる
2. 反証。出てきた指摘を別のエージェントに渡して、1 件ずつ「本当に問題か」を素材に当たって検証させる。round 1 で 51 件、round 2 で 22 件。半分以上は反証で落ちる
3. 判定。残ったものを私が読んで採否を決め、修正する

指摘は「ファイル / 時刻 (source 秒とタイムライン秒) / 何が / なぜ問題 / どう直すか」の形で出させる。推測で断定させない。確認できないものは「未確認」と書かせる。

モデルの割り当ては YD 指示 (2026-09-16 01:27) に従い、洗い出し・反証・実装・FCP 操作は Opus と Sonnet、頭を使う判断だけ Fable。

## 判断の材料は目と耳ではなく機械検査で作る

指摘の当否を決めるとき、印象で判断すると v2 と同じことになる。3 つの機械検査を根拠にした。

カット境界は、verbatim ASR の単語タイムスタンプ + 10ms RMS + 該当箇所の再文字起こし。再文字起こしの窓は 2〜6 秒。10 秒を超えると whisper が存在しない文を返すので使えない。

丸窓の顔判定は、焼いた素材を 4fps でデコードして YuNet で顔検出、SFace で話者本人との類似度を測る。類似度 0.4 以上、顔幅 70px 以上、顔が円の中、の 3 条件で valid にする。類似度を見ないと、スクリーンに映った顔写真や集合写真を拾う。

FCPXML の構造は、生成後にスクリプトで検査する。リソースの実在、シーケンス長の一致、丸窓の連続長と位置、フェードの有無、ズームの連続性。DTD 検証は通っても、中身がおかしいことはいくらでもある。

## 成果物

構成v6_v2 (`_FCP納品/ハタチたち5説明会_構成v6_v2.fcpxml`)。4K 59.94p、本編 6:22.2 + エンドカード 6 秒、ショット 48、字幕 28 枚、丸窓 28 クリップ。DTD 検証 OK、構造チェック 0 件。

## うまく行ったこと

洗い出しと反証を別のエージェントに分けたのが効いた。洗い出し役は網羅を優先して過剰に挙げてくるが、反証役に通すと残るのは 2 割以下になる。1 人のエージェントに「挙げて、かつ正しさも保証しろ」と言うと、挙げる数が減って本当の不良を落とす。

既知の制約を先に文書化して渡したこと。話者がフレーム外にいる約 100 秒や、SV で丸窓を置いていない理由を書いておかないと、毎回同じ指摘が返ってきて判定の時間を食う。

機械検査の出力をそのままエージェントに渡せる形 (境界ごとの単語と RMS を並べたテキスト、丸窓の類似度シート) にしておいたこと。画像や音を「見せて」判断させるより、数字で出したほうが判定が早いし再現する。

丸窓の追跡が外れた区間を、焼いた素材ではなく 4K 原本から追い直して小さい修正素材だけ焼き直す方式。19GB を焼き直さずに済んだ。

## 詰まったこと

v3 の引き継ぎ時点で「監査は未実施」と書いて次のセッションに渡したが、その時点で不良が残っていることは分かっていなかった。引き継ぎ前に最低限の機械検査だけでも通しておけば、v3 を YD に見せる寸前まで行かずに済んだ。

反証エージェントが素材に当たらずに「妥当」と返してくることがあった。検証手順 (どのファイルのどの時刻を見て判断したか) を書かせないと、反証が形だけになる。

エージェントの数を増やしても判定は速くならない。round 2 で 47 エージェント動かしたが、確定したのは 3 件だった。観点を増やすより、1 観点あたりの検証を深くしたほうがいい。

## 次回同じことをするときのチェックリスト

- [ ] `AUDIT_CONTEXT_*.md` を先に書く。何を作っているか / クライアント要求 / 既知の制約 (指摘不要) / ファイルの場所と読み方 / 指摘の出し方
- [ ] 洗い出しと反証は別のエージェントに分ける。同じエージェントに両方やらせない
- [ ] 反証には検証手順 (見たファイルと時刻) を書かせる
- [ ] 判定は自分でやる。エージェントの「妥当」「問題なし」をそのまま採用しない
- [ ] カット境界は verbatim 単語タイムスタンプ + RMS + 2〜6 秒窓の再文字起こしで確定する。10 秒超の窓は使わない
- [ ] 顔追跡の valid は本人類似度で判定する。検出できたかどうかだけでは足りない
- [ ] 生成後に構造チェックを走らせる。DTD 検証は通過の最低条件であって品質の証明ではない
- [ ] 引き継ぐ前に機械検査を 1 周通す。「監査は未実施」で渡さない
- [ ] 同じ観点で 2 周目を回すときは、エージェント数を増やさず検証を深くする

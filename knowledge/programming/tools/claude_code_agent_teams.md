# Claude Code — エージェントチーム機能 (実験的)

> 複数の Claude Code インスタンスをチームとして連携させる実験的機能。リーダー (作業を調整) + メンバー (独立した Claude インスタンス) の構造。
>
> 要求バージョン: Claude Code v2.1.32+
> 公式ドキュメント: https://docs.claude.com/ja/agent-teams
> 有効化: 2026-05-21 ([[2026-05-21_エージェントチーム機能_有効化]])

---

## 🎯 何ができるか

- 複数の Claude Code セッションが**互いに通信しながら**並列作業
- 共有タスクリスト + メールボックスで自己調整
- リーダーは各メンバーに直接メッセージ送信可、メンバー間も同様
- メンバーごとに独立コンテキストウィンドウ → 干渉しない

## 🔀 既存の subagents との違い

**最重要**: Claude Code には「サブエージェント」と訳される概念が**2つ**ある。YD と話す時はどちらか明確にする。

| 観点 | subagents (既存) | エージェントチーム (新、実験的) |
|------|----------------|---------------------------|
| **起動方法** | `Agent` ツール呼び出し | `TeamCreate` でチーム作成、メンバー生成 |
| **通信** | メインエージェントにのみ結果返す | メンバー同士で直接メッセージ送受信 |
| **調整** | メインがすべて管理 | 自己調整、共有タスクリスト |
| **コンテキスト** | 独立、結果を要約してメインに返す | 完全に独立、メインに会話履歴は引き継がれない |
| **最適な用途** | 結果のみが焦点な軽い委任 (調査・レビュー) | 議論・相互検証・大規模並列 |
| **トークン** | 低 (要約のみメインに返る) | 高 (各メンバーが個別 Claude) |

実用判断:
- 「3 視点で同じ問題を独立調査して、お互いの主張を批判し合う」 → **エージェントチーム**
- 「コードベース内の X を grep してこい」 → **subagents** で十分

## 🟢 [[parallel_claude]] との違い

YD は既にヘッドレス並列の自走基盤 [[parallel_claude]] を持っている。エージェントチームと棲み分けが大事。

| 観点 | parallel-claude (既存自作) | エージェントチーム |
|------|------------------------|----------------|
| **モード** | `claude -p` (ヘッドレス、stream-json) | 対話型セッション内で並列 |
| **通信** | 各セッション独立、ファイル経由でのみ間接連携 | チーム内で直接メッセージ送受信 |
| **コスト** | $0 (Max 20x 完結、OAuth) | 線形 (メンバー数 × トークン) |
| **監視** | `monitor.sh` + cron で `ps aux` 検出 | リーダー自身が全メンバー状態を把握 |
| **適性** | バッチ・夜中の長時間自走・"寝てる間に走らせたい" | 議論・検証・"今この場で 5 視点欲しい" |

棲み分けルール (YD の Max 20x 枠の活用方針 [[2026-05-19_API依存撤廃_Max20x完結化]] とも整合):
- **夜間バッチ / 長時間自走** → parallel-claude
- **対話 + 議論 + 短時間集中** → エージェントチーム

## ⚙️ 有効化

### settings.json (グローバル)

`~/.claude/settings.json`:

```json
{
  "permissions": { ... },
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "model": "opus[1m]",
  ...
}
```

### 表示モード

| モード | 動作 | 必要なもの |
|--------|------|----------|
| **in-process** | 全メンバーがメインターミナル内で動作。Shift+Down でメンバーをサイクル、Enter でセッション表示、Escape でターン中断、Ctrl+T でタスクリスト切替 | 何もいらない、どのターミナルでも動く |
| **分割ペイン** | 各メンバーが独自のペイン、すべてのメンバー出力を同時に見渡せる、ペインクリックで対話 | tmux または iTerm2 + it2 CLI |
| **auto** (デフォルト) | tmux 内で起動なら分割ペイン、そうでなければ in-process | 自動判定 |

明示するには:
```json
{ "teammateMode": "in-process" }  // 強制 in-process
{ "teammateMode": "tmux" }        // 強制 分割ペイン (tmux か iTerm2 を自動選択)
```

### 分割ペインを使うときの起動順

```bash
tmux           # tmux セッション起動 (重要)
claude         # この中で起動すれば自動で分割ペインモード
```

**注意**: Claude Code を tmux **外** で起動すると、teammateMode が `auto` でも in-process になる。これは仕様。tmux 内で起動するクセを付けるか、ターミナル起動エイリアスに仕込む。

## 🏗 アーキテクチャ

```
チームリーダー (作成セッション)
├── 共有タスクリスト (~/.claude/tasks/{team-name}/)
├── チーム設定 (~/.claude/teams/{team-name}/config.json)
├── メールボックス (エージェント間メッセージング)
│
├─ メンバー1 (独立 Claude Code)
├─ メンバー2 (独立 Claude Code)
└─ メンバーN (独立 Claude Code)
```

- 各メンバーは生成時に通常のプロジェクトコンテキスト (CLAUDE.md, MCP, skills) をロード
- リーダーの会話履歴は引き継がれない → 生成プロンプトに必要な情報を全部書き込む
- メンバーが他のタスクが依存するタスクを完了すると、ブロックされたタスクが自動的に解除
- リーダーは固定 (一度作ると入れ替え不可、チームの生涯は同じセッション)

## 🛠 主要ツール (deferred tools として注入される)

エージェントチーム機能が有効になると、以下が `<system-reminder>` 経由で deferred tools として利用可能になる。実際に呼ぶには `ToolSearch` で `select:` してロード。

| ツール | 用途 |
|-------|------|
| `TeamCreate` | チーム作成、メンバー生成 |
| `SendMessage` | 任意のメンバー (もしくはリーダー) にメッセージ送信 |
| `TeamDelete` | チームのクリーンアップ |

メンバー生成時に subagent 定義 (`security-reviewer` など) を **チームメンバーのロール**として再利用できる。ただし subagent 定義の `skills` と `mcpServers` frontmatter は適用されない (メンバーは通常のセッションと同じくグローバル/プロジェクト設定からロードする)。

## 🎨 使い方の典型パターン

### パターン1: 競合する仮説でデバッグ

```text
ユーザーが「アプリが1メッセージで終了する」と報告。
5人のメンバーを生成して、それぞれ違う仮説を独立調査してください。
お互いに反証を試みる科学的議論の構造で進めて、
合意が形成された仮説を findings.md に書いてください。
```

→ 議論構造により、1 つの理論にアンカリングするバイアスを回避できる。

### パターン2: 並列コードレビュー

```text
PR #142 を 3 人で並列レビューしてください:
- セキュリティ
- パフォーマンス
- テストカバレッジ
各自独立で見て、最後に統合レポート。
```

→ 単一レビュアーだと得意な観点に傾く問題を回避。

### パターン3: 新機能の並列実装

```text
4 人で次のモジュールを分担実装:
- メンバー1: バックエンド API (src/api/auth.ts)
- メンバー2: フロントエンド (src/components/login/)
- メンバー3: テスト (tests/auth/)
- メンバー4: ドキュメント (docs/auth.md)
ファイル所有を分けたので競合しません。
```

→ ファイル所有を切るのが鉄則 (同じファイルを 2 人が編集すると上書き発生)。

### パターン4: 多視点リサーチ深化 (Arte Grow ケース)

既存リサーチを入力に、5視点で深化:
- 経済性 / 倫理 / オペ / 競合 / Devil's Advocate

→ Devil's Advocate を必ず 1 人入れるとアンカリングを防げる。

## 💡 ベストプラクティス

1. **チームメンバーに十分なコンテキストを提供**: 会話履歴は引き継がれない。生成プロンプトにタスクの詳細を全部書く。
2. **チームサイズは 3〜5 人**: 多くても良いが、調整オーバーヘッドと収穫逓減のバランスから 3〜5 が現実的。
3. **タスクを適切にサイズ設定**: チームメンバーあたり 5〜6 個のタスクが目安。
4. **ファイル所有を分ける**: 2 人が同じファイルを編集すると上書き発生。
5. **監視と操舵**: 長時間無人で走らせると無駄な努力が増える。途中で見て方向修正する。
6. **小さく始める**: 初回はコードを書かないタスク (レビュー・調査) から。実装系は並列でやると競合する。
7. **クリーンアップ**: 終了後 `TeamDelete`。リーダーから実行する (メンバーから呼ぶとリソースが不整合になる)。

## ⚠️ 制限事項

- **セッションあたり 1 つのチーム**: 同時に複数チームは作れない、現チームをクリーンアップしてから次へ。
- **ネストされたチームなし**: メンバーが自分のチームを生成することはできない。
- **リーダーは固定**: チーム作成セッションが生涯リーダー、譲渡不可。
- **`/resume` と `/rewind` は in-process メンバーを復元しない**: 再開後、リーダーが存在しないメンバーにメッセージを送ろうとすることがある。再生成すればOK。
- **タスクステータスが遅延することがある**: タスクが立ち往生したら、リーダーに「進捗確認」をナッジする。
- **権限は生成時に固定**: メンバーごとの permission モードは生成時のみ。後から変更不可。

## 💰 コスト感

- メンバー 1 人 = 独立した Claude Code セッション = 独立した課金
- 5 メンバー深い議論 → 単一セッションの 5〜10 倍のトークン消費が目安 (各人の独自コンテキスト分)
- バッチ系は [[parallel_claude]] (Max 20x 完結、$0) で代替する

**実測値**: 試走後にここに追記する。

## 📌 トラブルシューティング

- **メンバーが表示されない**: in-process なら Shift+Down で切替、tmux なら `which tmux` 確認、iTerm2 なら `it2` インストール + Python API 有効化を確認
- **権限プロンプトが多すぎる**: メンバー生成前に [[claude_code_permissions]] で一般操作を事前承認
- **メンバーがエラーで停止**: Shift+Down または ペインクリックで出力確認、追加指示か置換メンバー生成
- **リーダーが作業完了前にシャットダウン**: 「メンバーが完了するまで待つ」と明示
- **孤立した tmux セッション**: `tmux ls` → `tmux kill-session -t <name>`

- 公式ドキュメントが日本語で完備されていて、用語のブレが少なかった

## ❌ 詰まったこと

- 「サブエージェント」用語の混同 → subagents (既存) と agent teams (新) を最初に切り分ける必要があった
- tmux 自動起動の不可 → 分割ペインを使うには YD が `tmux` → `claude` の順で起動する習慣をつける必要

## 📋 次回チェックリスト

エージェントチームを実戦投入する前に:

1. tmux で起動したか確認 (`echo $TMUX` で表示されれば内側にいる)
2. 5 人以下に絞ったか
3. 各メンバーのタスクが**ファイル単位で独立**しているか (同じファイルを書く 2 人がいたら上書き発生)
4. Devil's Advocate を 1 人入れたか (アンカリング防止)
5. 既存リソース ([[parallel_claude]] の中間成果物、`raw/research/` の既存リサーチ) を入力に渡せるか
6. プラン承認を要求するか (リスクが高い変更なら yes、調査なら no)
7. 終了後 `TeamDelete` でクリーンアップする予定があるか
8. 試走後に実測トークン消費をこのファイルの「コスト感」セクションに追記する
